# Agent Note: 以项目级安装试用通用 Harness Skills

Status: implemented

## Problem

研究仓库把原 DSH Skills 降级到 `research/cases/skills/` 后避免了产品命令在错误仓库中自动触发，但也使提取出的 Harness 只剩规则和结构说明。项目会话无法发现真实 Skill 名称，也不能通过实际调用判断哪些工作流有价值。直接全局安装尚未稳定的 Skills 又会把未验证行为同时带入所有项目，无法隔离试用反馈。

## Decision

当前分支作为通用 Harness Skill 的源仓库，在 `.agents/skills/` 保存删除 DSH 路径、包名、命令、分支和产品政策后的标准源码。`dsh-harness-kit` 与后续试用仓库是同级项目，通过项目自己的 `.agents/skills/` 安装一份副本；项目可以单独筛选调用和启用策略，但通用修正必须同时回写源仓库和正在试用的项目副本。

项目特例归项目 `AGENTS.md`，不进入通用 Skill。GitHub 是当前个人使用环境，可以保留 GitHub 专用 Skills 和集成，但 fork 双主线、具体分支名、项目检查命令、文档站结构和双语配对契约不得成为通用默认。全局安装留到项目级试用证明 Skills 稳定之后。

采用以下版本链：

| 版本 | Todo | Deferred | Constraint | 验收条件 | 待裁决项 |
| --- | --- | --- | --- | --- | --- |
| S1 — 项目级 Skill 基线 | 通用化原 Skills；在源仓库与 Kit 安装同名副本；验证 frontmatter、引用和辅助文件。 | 全局安装、发布工具、自动同步。 | 不写入具体项目命令或 fork Profile；不替用户决定最终启用集合。 | 新 Kit 会话能够发现 Skill 名称；两仓库 Skill 内容一致；源仓库仍保留固定历史证据。 | Kit 中每个 Skill 的隐式或显式调用策略。 |
| S2 — 项目反馈修正 | 在真实项目任务中试用；将误触发、缺失输入和产品残留同步修正到两仓库。 | 跨项目自动升级。 | 项目反馈不能直接污染通用源码；项目事实留在项目规则。 | 每个保留 Skill 至少有一次真实调用结果或明确的暂不使用结论。 | 哪些 Skills 进入稳定集合。 |
| S3 — 稳定分发 | 为稳定集合确定版本、安装和回滚方式；再考虑全局发现路径。 | 未稳定和项目专属 Skills。 | 全局版本必须可追溯、可回滚，项目特例继续分离。 | 新会话在不同项目中发现同一稳定版本，项目无需复制修改通用 Skill。 | 全局安装使用复制、链接或后续安装工具。 |

## Alternatives considered

- **继续只保存历史案例**：最安全，但不能验证 Skill 加载和真实使用，已经不符合快速采用目标。
- **立即全局安装**：减少项目复制，但任何误触发都会影响所有项目，当前缺少足够试用证据。
- **只在 Kit 维护 Skills**：能快速试用，却会让项目副本成为事实源并随项目需求侵蚀，无法保持通用版本纯净。
- **把项目配置写入 Skill**：首次使用更直接，但每个项目会产生不同 Skill 分叉；项目事实应由作用域规则提供。

## Consequences

- 源仓库重新拥有可发现的活跃 Skills，历史原文继续保存在固定提交和 `research/cases/skills/`，两者不能混为当前权威。
- 项目级副本在稳定前允许独立筛选，但通用内容修正需要人工同步两个仓库；当前接受这项少量重复维护成本。
- GitHub 专用工作流可以保留清楚的 provider 边界，项目分支模型和检查命令仍由项目自己声明。
- S1 不承诺全部 Skills 已值得长期启用，只承诺它们已去除明显 DSH 产品绑定、能够被加载并进入实际筛选。
