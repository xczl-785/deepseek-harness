# Agent Note: 通过现场还原研究 DSH 开发 Harness

Status: implemented

## Problem

保留的 Agent Notes、Skills、脚本、质量门禁和事故记录分别描述了 DSH 开发 Harness 的一部分，但逐份分类或总结无法说明它们在真实开发中如何配合。直接从单个工具抽象原则还会把文档声明误当成实际行为，把一次做法误当成稳定机制，或者在缺少提交、PR 和运行证据时补写并未发生的过程。

研究仓库需要一种成本受控的研究方法：先恢复一次具有代表性的开发活动，再解释任务、参与者、规则、工具、状态、反馈和持久证据之间的关系。该方法不能要求恢复完整产品仓库、建设研究平台或把全部历史工具通用化。

## Decision

本仓库采用“现场还原、关键步骤重放、跨现场验证、有限提炼”的研究路线。研究单位是一次有明确触发、过程和结果的开发活动，不是一个孤立文件或工具。完整目标是形成有来源、可复核、说明适用限制的 DSH 开发 Harness 运作模型；模型能够解释实际行为，也能区分 DSH 专属做法与可迁移方法。

### 现场选择

优先选择证据完整且能观察多个 Harness 组成部分协作的现场。每个现场先声明研究问题、代表性、时间或提交范围、可用证据和已知缺口。首个现场研究“一次非平凡改动从开发完成到安全推送”，因为现有语料同时保留了变更范围、Agent Note、定向检查、Git hook、pre-push、CI 和评审相关证据。第二个现场优先选择 stacked PR 的评审与落地，用于检查第一现场得到的 Git、门禁和人工判断结论。

### 证据等级

- **直接事实**：固定提交中的文件、Git 对象、PR 或 review 记录、运行日志、测试输出等原始材料明确证明的内容。
- **证据支持的还原**：多个直接证据共同支持，但没有单一材料完整记录的过程或关系。
- **研究推断**：能够解释现象、仍需重放或其他现场验证的假设。
- **未知项**：现有证据无法恢复的状态、时序或动机。

研究记录必须按以上等级表达结论。不得把推断写成实际发生的行为，也不得为了得到完整时间线而隐藏未知项。DSH 产品事实以 [source lock](../../../../research/source-lock.json) 固定的官方提交为起点；需要更多历史时记录额外 commit、PR 或 URL，不移动 source lock 的原始提取身份。

### 研究步骤

1. **固定现场**：记录任务、源码与分支状态、参与者、当时生效的规则、预期结果和研究边界。
2. **收集证据**：连接 Agent Notes、AGENTS、Skills、脚本、配置、commit、PR、review、CI、测试与事故记录，并说明每项证据能证明什么。
3. **还原过程**：按可证明的时间或因果顺序描述触发、选择、操作、门禁反馈、修正和最终证据；无法排序的事件保持未排序。
4. **重放关键步骤**：所有现场完成文档还原；仅在现有脚本或临时固定 checkout 足以验证关键机制时进行局部重放；只有因果关系仍不明确时才做绕过或替换机制的对照实验。
5. **解释机制**：说明输入、参与者责任、保存状态、阻止条件、反馈路径、人工裁决点和输出，不把“存在某文件”当成“机制实际生效”的证明。
6. **跨现场验证**：用第二个具有差异的现场检查同一关系是否重复出现，并标出稳定机制、任务偶然做法、DSH 专属约束和可迁移候选。
7. **有限提炼**：先形成研究结论；只有重复使用价值明确、适用范围可说明且用户接受时，才提取 Skill、脚本、fixture 或稳定方法文档。

### 研究产出

每个现场默认只新增一份 `research/studies/yyyy-mm-dd-topic.md`，包含研究问题、现场范围、证据清单、还原过程、重放结果、机制解释、事实与推断、未知项、暂定结论、适用限制和下一现场需要验证的内容。只有可执行重放确实需要时，才在同名目录旁增加最小 fixture；不得为展示、索引或文档依赖关系新增工具。

研究结论分为三级：单现场支持的是“暂定发现”；两个不同现场支持的是“稳定发现”；经过适用范围分析并获得用户接受后，才成为“可复用方法”。研究成果若适合 DSH 产品，必须通过产品仓库中的独立分支和评审显式移植，研究分支不整体合回产品主线。

### 生命周期

本记录是研究方法的稳定规则，truth source 是用户接受的研究出发点与本仓库保留的可核验证据，downstream target 是 S1–S4 的研究记录。每个现场记录是 bounded process material：创建后处于 `working`，完成证据复核后转为 `closed`；稳定结论吸收到后续综合记录，现场文件则作为证据保留。S4 完成后，本记录继续约束新现场，只有新的已接受研究方法完整取代它时才退出当前规则面。

## Alternatives considered

- **按 Skills、Notes、脚本和 CI 分类分别研究**：适合清点材料，但会丢失它们在同一任务中的时序、反馈和责任关系，因此只作为现场取证手段。
- **先建立完整 Harness 架构模型，再寻找例子**：模型会先于证据形成，容易把仓库声明重述为结论，因此不采用。
- **恢复完整 DSH 开发环境后进行全流程复刻**：成本高，且环境差异会遮蔽真正要验证的机制；只在具体推断需要时使用临时固定 checkout 重放最小路径。
- **只分析事故和失败案例**：事故能暴露缺失门禁，但不能独立证明日常流程如何工作；事故作为正常现场的对照证据。
- **为研究材料建设索引、依赖图或知识库**：当前语料规模可以通过导航和搜索直接使用，工具成本不会提高研究结论质量，因此不采用。

## Consequences

- 研究开始速度取决于现场证据完整度，而不是材料数量；首个候选现场证据不足时应更换，不扩大工具建设。
- 单个现场不会直接产生“最佳实践”，研究记录需要保留不确定性并等待第二现场验证。
- 产品源码只在临时固定 checkout 中作为证据或重放环境使用，研究仓库继续保持精简。
- 研究产出默认是一份可复核记录，不自动增加 Skill 或脚本；工具化成为需要单独接受的后续决定。
- 现场还原可能发现现有历史材料互相冲突；此时保留冲突、回到直接证据，不改写历史案例来制造一致。
